# meeting-room-booking

## Запуск

```sh
pnpm install
pnpm dev
```

Проверки: `pnpm test`, `pnpm build`, `pnpm lint`.

## E2E

```sh
pnpm exec playwright install chromium --no-shell
pnpm test:e2e
```

Playwright сам собирает приложение, запускает preview на `127.0.0.1:4175`
и останавливает сервер после тестов. Порт должен быть свободен.
Тесты работают с настоящим MSW в production demo, без подмены HTTP-ответов.
Для каждого теста создаётся отдельный браузерный контекст; время фиксировано
на 9 октября 2026, 08:00 в `Asia/Bishkek` до загрузки приложения.

Сценарии CRUD, серверного 409 при создании и редактировании, клавиатуры
и адаптивной вёрстки запускаются в Chromium на ширинах 1280 и 375 px.
Отчёт: `pnpm exec playwright show-report`. Скриншоты вёрстки и артефакты
ошибок сохраняются в `test-results/`, HTML-отчёт — в `playwright-report/`.
Эти каталоги исключены из Git. Unit/integration-тесты запускаются отдельно через `pnpm test`.

Страница позволяет выбрать дату и посмотреть бронирования по времени начала.
По умолчанию выбрана сегодняшняя дата в локальном часовом поясе браузера.
Предусмотрены загрузка, пустой список и повтор запроса при ошибке.
Запросы выполняются через TanStack Query с отдельным ключом для каждой даты;
HTTP-запрос вынесен в `src/features/bookings/api.ts`.

Форма на React Hook Form содержит необязательное название и время начала/окончания.
Дата синхронизируется с выбранным днём. При отправке `validateBooking` проверяет
поля с текущим временем и бронями выбранного дня; ошибки показываются у полей,
значения сохраняются. Создание заблокировано для прошлых дат, во время загрузки
или обновления списка и при ошибке запроса. Создание, редактирование и удаление
с подтверждением выполняются через API. При серверном конфликте список обновляется,
а поля формы сохраняются. В блоке «Демо-сценарии» можно включить одноразовый конфликт.

Стили написаны на Tailwind CSS через `@tailwindcss/vite`. Общая тема и подключение
Tailwind находятся в `src/index.css`, классы компонентов — в JSX.

## Mock API

MSW запускается до рендера React в разработке и в production demo.
Дополнительные переменные окружения не нужны. Проверить production demo локально:

```sh
pnpm build
pnpm preview
```

Для публикации используйте содержимое `dist`, включая `mockServiceWorker.js`.
Service Worker работает через HTTPS или на localhost.

Данные хранятся в памяти текущей вкладки: начальный список пустой,
перезагрузка страницы сбрасывает бронирования. Между вкладками данные не синхронизируются.
Хранилище вынесено в `src/mocks/bookings-store.ts` и передаётся обработчикам явно.
Дата и время интерпретируются в локальном часовом поясе браузера.

| Метод | URL | Результат |
| --- | --- | --- |
| GET | `/api/bookings?date=YYYY-MM-DD` | `200`, массив броней на дату, по времени начала |
| POST | `/api/bookings` | `201`, созданная бронь с серверным `id` |
| PATCH | `/api/bookings/:id` | `200`, обновлённая бронь; поддерживается частичное обновление |
| DELETE | `/api/bookings/:id` | `204`, без тела ответа |

POST принимает `date`, `start`, `end` и необязательный `title`.
PATCH принимает любое подмножество этих полей и сохраняет остальные значения.
Даты передаются как `YYYY-MM-DD`, время — `HH:mm`. Передавать `id` в теле нельзя.

Ошибки возвращаются как `{ code, field?, message }`:

- `400`: неверный JSON, типы полей или нарушение правил бронирования;
- `404`: бронь для PATCH/DELETE не найдена (`not_found`);
- `409`: пересечение с другой бронью (`conflict`, поле `start`).

POST/PATCH используют общую `validateBooking` и проверяют актуальное состояние
mock-хранилища. Неуспешная операция не изменяет данные.
